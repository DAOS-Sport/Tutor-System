## 二、已完成內容（逐 Phase，含檔案位置）

### Phase 0：家長/學員 Ragic 識別鍵修復（根治「熊韋程」bug）
**檔案**：`server/bootstrap/coreSchema.js`、`server/services/parentSync.js`

- **Root cause 確認**：`parents` 表原本以 `phone` 做 `ON CONFLICT` upsert 鍵，`ragic_record_id` 只是隨行欄位。Ragic 端電話被改掉/打錯時，本地會孤立舊列或誤合併。migration 010 想加的 `uq_parents_ragic_record_id` 唯一索引從未被自動執行（`db/migrate.js` 只能手動 `npm run db:migrate`，未接入開機 `bootstrapCore()`）。
- **修復**：
  1. `coreSchema.js` 新增 DO 區塊：對 `parents`/`students` 的 `ragic_record_id` 做**安全去重**（不刪除任何列，只解除重複列的佔用，優先保留有 line_uid/較新的一筆）+ 建立真正的 `uq_parents_ragic_record_id`/`uq_students_ragic_record_id` UNIQUE 索引，每次開機冪等執行。
  2. `parentSync.js` 的 `upsertLocalParent`：`ragic_record_id` 非空時改用 `ON CONFLICT (ragic_record_id)`（phone 只作 fallback），Ragic 換號時直接就地更新 phone 欄位，不再孤立舊列。
  3. 新增 `preservePending` 參數（預設 true，比照 students 既有機制）：本地未回寫 Ragic 的編輯（`last_synced_at IS NULL`）不被夜間 pull 覆蓋。兩個呼叫端（`_syncWithLock` 即時登入路徑傳 false、`_pullParentsStudentsImpl`/現已改名 `_reconcileZ01FromShadowImpl` 夜間批次傳 true）已正確接線。
  4. `upsertLocalStudents` 第三層(name+birth)比對不再靜默覆蓋既有列，改建新列 + 寫入新表 `ragic_student_match_review` 供人工複核（避免同名學員誤判成同一人）。
- **測試**：三項機制皆已對照真實 Postgres 做過隔離測試（同 ragic_record_id 換電話→就地更新無孤兒列；preservePending 保留本地待同步姓名；tier3 命中改建新列+寫入複核表且不被權威掃尾誤刪），測試腳本測完即刪除，未留在 repo。

### Phase 5：今日補的 4 個後端缺口（已完成 + 已對本機 dev server 做 live 驗證，非只有語法檢查）
比對 Chumg 重貼的完整「修改 PROMPT」規格，發現後端骨架有 4 處跟規格對不上，已修：

1. **`POST /register`（S4 REGISTER_NEW，flowToken 版）**：規格 §3.2 明定 flowToken 只能被 verify-phone/verify-student/bind/**register** 四端點接受，但舊骨架的 `/parent-register-line` 完全沒掛 flowToken。做法：把原本 350 行左右的核心註冊邏輯抽成共用函式 `_registerParentCore(req, res, resolveLineUid)`（`resolveLineUid` 是個 callback，驗證完表單欄位「之後」才呼叫，刻意維持原本 legacy 端點「先驗表單、再驗身分」的順序，重構途中一度不小心把順序顛倒，已抓到並修回來）；legacy `/parent-register-line` 傳入「解出 id_token」的 resolver，新 `/register` 傳入「直接回傳 `req.flow.lineUid`」的 resolver。**新增規則**：新端點若偵測到 flowToken 帶有 `phone`（代表是 S3 驗證失敗 3 次的 phone_collision 轉入，不是 S2 全新電話），不論表單填什麼，一律導去 Z03 待審（`pending_review`），不完成正式註冊、不建第二筆同電話 parent 記錄——已用真實 flow token 打過，行為正確。
2. **verify-phone 限速鍵改成 UID+IP**：規格 §3.5 要求「每 UID+IP 限速」，舊骨架只用 IP。改法：把 `router.post('/verify-phone', ...)` 的中介層順序從 `verifyPhoneRateLimit, requireFlowToken` 對調成 `requireFlowToken, verifyPhoneRateLimit`（讓 `req.flow.lineUid` 先就緒），`verifyPhoneRateLimit` 的 rate-limit map 鍵值改成 `` `${ip}:${lineUid}` ``。已用同一支 flow token 連打 6 次驗證第 4 次起變 429。
3. **verify-phone 回應時間拉平**：found（要多打一次 Ragic）跟 not_found 分支原本執行路徑長短不一，構成時序側信道。改法：整支 handler 包一層 `respond(status, body)`，量測從進入 handler 到現在的耗時，補到固定下限 `VERIFY_PHONE_MIN_MS = 400ms` 才真的送出回應。已量測驗證（兩種分支耗時都落在 400ms 上下）。
4. **`requireParent` 對錯誤 type 的 token 從 403 改回 401**：規格 §7 PASS 判準明講「以 flowToken 打 `/api/courses/mine` → 401」，但舊 `requireParent` 對 `type !== 'parent'` 回的是 403（洩漏「這是一個型別不對但有效的 token」）。已確認 repo 內無任何地方依賴這個 403（grep 前後端皆無命中），改成 401 + `PARENT_TOKEN_REQUIRED`；已用真實 flow token 打 `/api/courses/mine` 驗證回 401。

驗證方式：本機 dev server（`node index.js`，pid 129，非 nodemon、不會自動 reload）已徵求同意後重啟為 `npm run dev`（nodemon，之後編輯會自動 reload），用 `signFlowToken()` 簽真的 flow token 對本機 `localhost:3999` 實際打過以上所有端點，非只跑 `node --check`。
